将工作卸载到 worker 池的好处将根据工作负载的不同而有很大差异。在某些情况下，worker 池实际上可能会损害性能。必须仔细考虑。

在此示例中，我们在引入 100 毫秒的人为延迟后，创建一个简单的 Fastify http 服务器，该服务器响应一个简单的 JSON 对象。

服务器有四种变体：

* async-sleep-unpooled - 使用 Promise 包装的 `setTimeout` 进行异步延迟。允许事件循环在延迟期间继续转动，从而允许服务器响应其他请求。延迟发生在主线程中。

* async-sleep-pooled - 将异步延迟移动到 worker 线程进行处理。

* sync-sleep-unpooled - 使用 `Atomics.wait` 进行同步延迟，将主线程阻塞 100 毫秒后再响应。由于主线程被阻塞，我们在等待时事件循环不会转动。这模拟了一个特别昂贵的事件循环阻塞场景。

* sync-sleep-pooled - 将同步延迟移动到 worker 线程进行处理。

:::note
对于 `async-sleep-pooled` 和 `sync-sleep-pooled`，主线程都使用 Promise 等待 worker 完成其任务，然后再响应请求。
:::

## 设置
此示例的代码文件可以在 [github](https://github.com/piscinajs/piscina/tree/current/examples/server) 上找到。

首先，运行 `npm i` 安装依赖项。我们使用 [`autocannon`][] 对这四种变体进行基准测试：

```console
$ npm i -g autocannon
```

```console
$ node async-sleep-unpooled
```

## 调整池性能

可以使用各种选项调整 Piscina worker 池的性能：

* `minThreads` - 始终运行的最小线程数
* `maxThreads` - 允许的最大线程数
* `idleTimeout` - 允许线程保持空闲的毫秒数
* `maxQueue` -- 待处理工作项的最大数量
* `concurrentTasksPerWorker` -- 并发分发给单个线程的工作项数量。

在本示例中，我们将使用 `idleTimeout` 和 `concurrentTasksPerWorker`。

默认情况下，一旦 Piscina worker 线程无事可做，它就会终止。这意味着如果工作队列为空，线程将终止。如果我们没有保持队列填充，这将产生额外的开销，因为 Node.js 会启动新的 worker 线程来处理传入的请求。

同样在默认情况下，Piscina 假设作业本质上是同步的，并且在任何时候每个线程只分发一个作业。如果工作负载是异步的，将 `concurrentTasksPerWorker` 设置为更高的数字将增加 Piscina 发送给单个 worker 的作业数量，允许它处理多个任务。

`async-sleep-pooled` 示例已编写为接受两个可选参数。第一个是 `concurrentTasksPerWorker`，第二个是 `idleTimeout`。要查看设置每个参数对示例性能的影响，请运行：

```console
$ node async-sleep-pooled 10 1000
```

然后再次运行 autocannon：

```console
$ autocannon localhost:3000
```
